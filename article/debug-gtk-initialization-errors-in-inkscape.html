Debug GTK Initialization Errors in Inkscape

When Inkscape fails to launch or crashes during startup, the issue frequently stems from GTK or GDK initialization problems. This guide outlines the specific command-line flags and runtime switches you can pass to Inkscape to capture detailed diagnostic traces, force synchronous rendering calls, and isolate GTK initialization errors directly from your terminal.

Core GTK and GDK Debugging Flags

Because Inkscape is built using the GTK toolkit, it accepts standard GTK and GDK command-line arguments directly. These flags alter how the toolkit initializes its display backends, windowing systems, and internal objects.

  • --g-fatal-warnings: Forces the application to abort immediately upon encountering any GLib or GTK warning or critical message. When used alongside a debugger, this generates an immediate core dump or breakpoint at the exact point of the initialization error rather than allowing it to cascade.
  • --gtk-debug=FLAGS: Enables specific GTK runtime debugging routines. You can pass individual categories or run --gtk-debug=all to output comprehensive traces of module loading, CSS parsing, geometry calculations, and widget layout during initialization.
  • --gtk-no-debug=FLAGS: Explicitly disables specific debug routines if a default configuration is generating excessive noise.
  • --gdk-debug=FLAGS: Traces the underlying GDK layer, which handles low-level windowing, event handling, and display initialization. Passing --gdk-debug=all logs every interaction with the display server (such as Wayland or X11) during startup.
  • --gdk-no-debug=FLAGS: Disables specific GDK debugging options.
  • --sync: Runs the X11 display connection in synchronous mode. This prevents asynchronous call buffering, ensuring that any X server error is reported immediately at the exact line of code that triggered it during startup.

Inkscape Diagnostic Flags

In addition to GTK-level arguments, Inkscape provides native flags to inspect the runtime environment:

  • --debug-info: Prints technical details regarding the operating system, Inkscape build configuration, GTK version, and linked graphics libraries. This helps verify if dynamic linkers are loading mismatched GTK libraries at launch.

Tracing with Environment Variables

While command-line flags handle most scenarios, GTK and GLib also evaluate specific environment variables during initialization before CLI parsing completes. These can be prepended directly to the launch command:

  • G_MESSAGES_DEBUG=all inkscape: Instructs GLib to print all diagnostic messages, including low-priority debug information that is suppressed by default.
  • GTK_DEBUG=interactive inkscape: Attempts to launch the GTK Inspector window alongside the application to inspect widget hierarchies and CSS rules, provided initialization gets far enough to map a window.
  • G_DEBUG=fatal-criticals inkscape: Directs GLib to crash on critical assertions, isolating the exact initialization failure.

Combining Flags with a Debugger

To trace an initialization crash to its source code origin, combine the fatal warning flag with the GNU Debugger (gdb):

gdb --args inkscape --g-fatal-warnings --sync

Once inside gdb, execute run. When the GTK initialization error occurs, the process will halt immediately, allowing you to run bt (backtrace) to pinpoint the exact GTK function, theme, or plugin causing the initialization failure.
