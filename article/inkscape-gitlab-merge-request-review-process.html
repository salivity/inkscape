Inkscape GitLab Merge Request Review Process

Before a merge request is accepted into the Inkscape codebase on GitLab, it must undergo a structured community review process designed to maintain code quality, cross-platform stability, and architectural integrity. This process requires passing automated continuous integration pipelines, adhering to Inkscape's coding standards, undergoing peer review by core developers, resolving all reviewer feedback, and receiving formal approval from an authorized project maintainer.

1. Preparation and Submission

Every contribution begins with a merge request (MR) targeting the development branch, typically master. The author must provide a clear title and description explaining the purpose of the changes, referencing any relevant GitLab issue numbers using closing keywords (e.g., Fixes #1234). Commits must be logically structured with concise, descriptive commit messages to facilitate review and maintain a clean Git history.

2. Automated Pipeline Validation (CI/CD)

Once an MR is opened or updated, GitLab CI/CD automatically triggers build and test pipelines across supported platforms, including Linux, Windows, and macOS. For an MR to be considered for merging, all automated jobs must pass:

  • Compilation: The code must build cleanly without fatal errors across all target operating systems.
  • Automated Tests: Unit tests and regression suites must pass to ensure the changes do not break existing functionality.
  • Code Formatting: The code must conform to Inkscape's formatting guidelines, often checked via tools like clang-format.

3. Community and Core Developer Peer Review

Inkscape relies on a collaborative peer-review model. Reviewers examine the code for:

  • Architecture and Design: Ensuring new code fits cleanly into Inkscape's modular structure and properly utilizes libraries such as GTK, 2geom, and libnrtype.
  • Code Standards: Verifying adherence to modern C++ conventions, memory management practices, and Inkscape-specific style guides.
  • Licensing and Legal Compliance: Ensuring all added code is compatible with Inkscape's GPLv2+ (or GPLv3+) licensing and contains proper copyright attribution.
  • User Interface and Usability: Confirming that any user-facing changes adhere to GNOME Human Interface Guidelines and project accessibility standards.

4. Addressing Feedback and Updating the Code

Authors are expected to respond directly to inline comments and general suggestions. When adjustments are requested, developers update their local branch and push new commits to the same branch. Once discussions are concluded, threads are marked as resolved. Reviewers may ask the contributor to rebase on the latest target branch and squash intermediate "fixup" commits prior to merging.

5. Final Approval and Merging

An MR cannot be merged until it receives explicit approval from at least one core developer or maintainer who has write permissions on the repository. Once approvals are granted, discussions are resolved, and the pipeline shows a passing status, an authorized maintainer merges the MR into the main repository, concluding the review process.
