How Inkscape Handles SVG Coordinate Precision Errors

Inkscape manages numerical precision and floating-point rounding errors by decoupling its high-precision internal geometry engine from the text-based serialization used when saving SVG files. While vector calculations are executed in memory using standard 64-bit IEEE 754 floating-point arithmetic, the final coordinates written to raw SVG path data are rounded according to user-configurable export settings. This article covers how Inkscape balances in-memory numerical accuracy, serialized XML coordinate truncation, relative path drift prevention, and transform matrix operations.

Internal Representation vs. SVG Serialization

During an active editing session, Inkscape relies on its core geometric library, lib2geom. This library performs all geometric intersections, Bézier curve subdivisions, and node translations using standard C++ double types (64-bit double-precision floating-point numbers). This ensures approximately 15 to 17 significant decimal digits of precision during calculations, keeping internal rounding errors far below human visual perception or hardware display limits.

Rounding occurs primarily during serialization—the moment Inkscape translates internal in-memory structures into text-based SVG XML. Converting infinite or high-precision decimals into ASCII text can dramatically increase file size, so Inkscape truncates coordinates to a specified number of significant digits.

Configurable Numerical Precision Settings

Inkscape allows users to control floating-point truncation directly through its preferences:

  1. Navigate to Edit > Preferences > Input/Output > SVG output.
  2. Locate the Numerical precision setting.

This setting dictates the maximum number of decimal places or significant digits exported to attributes like d (path data), transform, x, y, width, and height.

By default, Inkscape sets this value to a level (typically 8 digits) that guarantees sub-pixel accuracy across virtually any canvas dimension while discarding negligible floating-point artifacts (such as 0.000000000000001 or 49.99999999999999). Lowering this value minimizes SVG file sizes, whereas raising it preserves minute geometric details for CAD, plotter, or CNC workflows.

Mitigating Cumulative Drift in Relative Paths

SVG paths support both absolute (M, L, C) and relative (m, l, c) commands. In a relative command chain, each point is defined as an offset from the preceding point. If truncated coordinates are continuously summed, small rounding discrepancies can compound, causing the terminal point of an open path or the closure of a closed path to drift noticeably from its intended position.

To counter this, Inkscape tracks the true, unrounded target coordinate in memory before generating serialized path strings. When outputting relative commands, the exporter computes offsets not from the ideal mathematical coordinates of the previous node, but from the already-rounded text position of the preceding node. This self-correcting mechanism prevents cumulative rounding drift across long chains of relative coordinates.

Transform Preservation vs. Baking

Coordinate precision is heavily influenced by how Inkscape handles transformations via the Store transformation preference, which offers two primary modes:

  • Preserved: Inkscape retains path data coordinates as originally drawn and appends a transform="matrix(...)" attribute to the SVG element. This isolates the base coordinates from repeated floating-point multiplication errors during successive moves, scales, or rotations.
  • Optimized (Baking): Inkscape recalculates every node’s absolute coordinate by applying the transformation matrix directly to the path data. While this produces cleaner SVG code without wrapper transform attributes, applying continuous transformations in this mode causes repetitive floating-point re-quantization, which can slightly degrade the precision of tight Bézier curves or coincident vertices over time.

Automatic Cleanup of Numeric Redundancies

Before writing raw coordinate data to the disk, Inkscape passes numerical strings through an internal SVG formatting pipeline. This formatter strips unnecessary trailing zeroes, converts negative zero representations (-0) to 0, and eliminates redundant spaces and coordinate separators (such as collapsing 0.5 -0.5 into 0.5-0.5). These micro-optimizations ensure that floating-point adjustments do not alter the semantic geometry of the SVG standard while keeping raw output clean and deterministic.
