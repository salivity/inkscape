Inspect Inkscape Memory Tree Using Debug Dialog

Inkscape relies on an internal representation of documents called the SPObject tree, which manages live C++ objects in system memory separately from the raw SVG XML markup. This guide explains how to open the Debug dialog, navigate the internal object memory tree, and inspect runtime object references, node types, and memory allocations for debugging and development purposes.

Understanding the Object Memory Tree

Inkscape maintains two parallel structural representations of any open vector file:

  1. The XML DOM Tree: The standard SVG source code, viewable through the XML Editor (Ctrl + Shift + X).
  2. The SPObject Memory Tree: The internal, live C++ object hierarchy that drives rendering, transformations, live path effects, and canvas interactions.

While the XML Editor displays attributes and tags, the Debug dialog exposes the underlying SPObject memory tree, showing live pointer addresses, reference counts, cache statuses, and internal signals.

Opening the Debug Dialog

Accessing internal debugging tools depends on your Inkscape build (standard release or development/debug build):

  1. Via Command Palette: Press ? (or Shift + Ctrl + P) to open the Command Palette. Type Debug and select the Debug dialog or internal memory inspector from the matching action list.
  2. Via Terminal or Launch Flag: If the option does not appear in standard menus, launch Inkscape from your terminal with developer options enabled: 
    inkscape --debug-info
    Alternatively, run Inkscape within a development environment built with CMAKE_BUILD_TYPE=Debug.
  3. Using GTK Inspector: On builds compiled with developer flags, press Ctrl + Shift + I or Ctrl + Shift + D to open the underlying GTK/Application Inspector to view active window objects and memory layouts.

Navigating the Internal Hierarchy

Once the Debug or Memory inspection interface is open:

  1. Locate the Document Root: Expand the top-level SPDocument node. This serves as the root container for all loaded document assets, definitions, and render layers.
  2. Expand the SPRoot Object: Directly beneath SPDocument, find SPRoot (corresponding to the <svg> tag).
  3. Traverse Child Nodes:
    • Expand branches to inspect structural containers like SPDefs (markers, gradients, patterns) and SPGroup (layers and grouped objects).
    • Identify leaf nodes such as SPShape, SPPath, SPText, and SPImage.

Inspecting Runtime Object Attributes

Selecting any individual node in the tree displays diagnostic memory details:

  • Object Pointer: Displays the hexadecimal memory address (e.g., 0x55d8f2a1b3c0) of the SPObject instance.
  • Type Identifier: Confirms the exact C++ runtime class implementing the node.
  • Reference Counts: Indicates how many active elements or internal listeners hold references to the object, useful for identifying memory leaks and orphaned elements.
  • Represented XML Node: Maps the selected memory object back to its linked Inkscape::XML::Node.
  • Clean/Dirty Flags: Shows whether the object requires a rendering update or transformation recalculation.

Diagnosing Issues with the Memory Tree

  • Ghost Objects: If an element is deleted from the canvas but still visible in the Debug tree, verify its reference count to ensure an extension, clone, or signal is not preventing garbage collection.
  • Live Path Effect (LPE) Stacks: Expand path elements to verify that linked LPE objects are properly attached and executing along the memory pipeline.
  • Clone Dependencies: Trace SPUse nodes back to their original source objects to ensure link integrity across document modifications.
