Libcroco CSS Cascade Handling in Older Inkscape

In older versions of Inkscape, prior to its transition toward an internal CSS engine and modern styling pipelines, CSS parsing and cascade resolution were delegated to the GNOME project's libcroco library. This article examines the internal architecture of libcroco, detailing how it constructs stylesheets, computes selector specificity, applies the CSS cascading order, and integrates with Inkscape’s native object tree to determine computed styles for SVG rendering.

Architecture of Libcroco's Cascade Engine

Libcroco models CSS cascading primarily through the CRCascade object, supported by the CRStyleSheet, CRStatement, and CRDeclaration data structures. When an older build of Inkscape loaded an SVG document containing external, embedded (<style>), or inline CSS, it leveraged libcroco’s SAC (Simple API for CSS) parser and document handler interfaces (CRDocHandler) to deserialize CSS text into structured C types.

The CRCascade structure acts as a container for multiple CRStyleSheet instances. Sheets are added to the cascade context using cr_cascade_append_sheet(). In the context of SVG processing, libcroco maintains distinct stylesheet layers to mirror the standard CSS cascading levels: User Agent defaults, user preferences, and author-defined styles.

Specificity Calculation and Selector Matching

To determine rule precedence, libcroco evaluates the specificity of every parsed selector chain. Selectors are represented internally via the CRSelector struct, which contains linked lists of simple selectors.

During selector evaluation, libcroco calculates specificity using the classic four-tuple model \((a, b, c, d)\):

  • \(a\) (Inline Styles): Flagged when declarations originate from a direct style="..." attribute rather than a stylesheet rule.
  • \(b\) (ID Selectors): Incremented for each #id component found in the selector chain.
  • \(c\) (Class and Attribute Selectors): Incremented for .class names, pseudo-classes, and attribute selectors.
  • \(d\) (Type Selectors): Incremented for element tag names and pseudo-elements.

Libcroco combines these components into an unsigned 32-bit integer weight. This packed representation allows rapid comparison between competing declarations: rules with higher mathematical values immediately override rules with lower values during sort operations.

The Cascade Resolution Sequence

When Inkscape queries computed properties for an element, libcroco executes the cascade algorithm across all matching declarations by following standard CSS2/CSS3 precedence rules:

  1. Origin and Weight: Declarations are grouped by origin (User Agent, User, Author) and the presence of the !important token. In libcroco, the !important attribute flips the precedence flag on a CRDeclaration, elevating an author rule above normal rules or prioritizing a user rule above author rules.
  2. Specificity Sorting: When two declarations share the same origin and importance, libcroco compares the pre-computed selector specificity. The declaration associated with the higher specificity weight wins.
  3. Source Order: If specificities are equal, libcroco falls back on document order. Statements registered later in the CRCascade stylesheet list—or lower within a single stylesheet—overwrite earlier declarations.

Integration with Inkscape's Object Tree

Inkscape mapped libcroco's cascading output to its internal SPStyle and SPObject representations. Because SVG specifications treat presentation attributes (such as fill="red") differently from CSS properties, Inkscape handled presentation attributes as baseline author styles with a specificity equivalent to zero.

When an SVG element (SPItem) required style re-computation:

  • Inkscape traversed its DOM-like XML representation (Inkscape::XML::Node) and passed element contexts to libcroco's matching routines.
  • Libcroco matched element tags, classes, and IDs against the active CRCascade rules.
  • The winning declarations were exported as a flattened list of name-value pairs, which Inkscape's sp_style_merge_from_dyanmic_target routines read directly into the element's SPStyle struct.

Performance and Obsolescence Factors

While libcroco provided a functional, spec-compliant cascade mechanism, its design required extensive heap allocation for GObject types and lacked support for incremental, dynamic style invalidation. For large SVG files with thousands of elements, recalculating cascades via libcroco produced significant memory overhead and processing latency. These limitations, combined with a lack of upstream maintenance and security patches, eventually led Inkscape to phase out libcroco in favor of faster, modern CSS parsing implementations.
